# Super Plumber v0.5.2 屎山代码与架构鉴定报告

- **审查日期**：2026-08-24
- **审查范围**：`src/core`（16 文件）、`src/cli`（25 文件）、`src/mcp/server.ts`、`src/web`（2 文件）、`src/index.ts`、`web-ui`（抽查）、`package.json`/`tsconfig.json`。总计约 7,500 行 TS。
- **方法**：逐文件精读 + 关键断言运行时验证（NaN→YAML 往返、artifacts 校验全库检索、MCP 工具注册计数、`server.listen` 绑定确认）。
- **红线遵守**：审查阶段未改动任何代码。
- **总体结论**：整体工程质量高于典型屎山——有状态机、锁、审计日志、缓存失效注释。但存在 **1 处可直接利用的命令注入**、**1 类成体系的路径穿越面**、**1 组"写入不校验、读取才校验"的数据毒化链**，以及 **CLI 与 MCP 双通道语义漂移**。S0 级问题必须在任何 npm 发布前修复。

## S0 — 安全与数据直接损害

### S0-1 【命令注入】`graph snapshot --git` 将用户消息直接拼入 shell 命令
- **位置**：`src/cli/snapshot.ts:18`
- `execSync(`git add .graph && git commit -m "snapshot: ${snap.id}${options.message ? ` — ${options.message}` : ""}"`)` —— `--message` 是用户自由文本，未做任何转义即插入 shell 字符串。`graph snapshot -m 'x"; rm -rf ~; echo "'` 即可执行任意命令（Windows 走 `cmd.exe`，Unix 走 `sh`）。
- **修复方向**：`execFileSync("git", ["commit", "-m", ...])` 数组传参，彻底不走 shell。

### S0-2 【功能全坏】同一行的 `git add .graph` 在 v0.5.2 布局下永远失败
- **位置**：`src/cli/snapshot.ts:18-21`（`cwd: rootDir`）
- `rootDir = cliGraphDir(process.cwd())` 返回的是**图目录**（如 `.graph/default/`），在该 cwd 下执行 `git add .graph` 是在找 `.graph/default/.graph`——不存在，`--git` 必然抛 "pathspec did not match"。此功能自多图改版后从未被测试覆盖（tests/ 无任何 `--git` 用例）。

### S0-3 【路径穿越】节点/边 ID 全链路无格式校验，直接拼接文件路径
- **位置链**：
  - 写入点：`src/core/parser.ts:63-65`（`nodeFilePath`）、`parser.ts:220-222`（`edgeFilePath`）；
  - 创建入口无校验：`src/core/node.ts:40-49`、`src/core/edge.ts:19-35` 只做 `existsSync`，不查 id 格式；
  - schema 层只查非空字符串：`src/core/schema.ts:246-247`（`reqString` 仅 `!== ""`）；
  - MCP 层 zod 同样裸 `z.string()`：`src/mcp/server.ts:630`（`graph_create_node` 的 id）、`:819`（`graph_add_edge` 的 id）。
- **后果**：ID 为 `../../evil` 时，`writeNode` 可把 YAML 写到图目录之外任意路径；`deleteNode`（`parser.ts:156-198`）可 rename 任意 `.yaml` 文件；`getNode` 可读任意 yaml。对比图名有严格校验（`src/core/graph-dir.ts:17,32-38` `GRAPH_NAME_RE`），节点/边 ID 却零校验。MCP 场景下 ID 由 LLM 供给，属真实的 confused-deputy 面。
- **次生面**：`src/core/docs-export.ts:145`（`docs/contexts/${c.id}.md`）同样以未校验 id 拼文件名。
- **修复方向**：在 `createNode`/`createEdge` 核心层加 `NODE_ID_RE`（如 `^[a-z0-9][a-z0-9_-]{0,63}$`），CLI/MCP/zod 同步收紧。

### S0-4 【文档撒谎】MCP 工具描述承诺的 artifacts 存在性校验根本不存在
- **位置**：`src/mcp/server.ts:1004` —— 描述写明 "artifacts 填真实文件路径 — **verification 层会实际检查它们存在**"。
- **事实**：全库检索 `artifacts` 的所有消费点（`src/core/node.ts:325-355`、`src/core/schema.ts:211`、`src/cli/get-node.ts:106-107`），没有任何代码检查文件是否存在。裁决 agent 依据该描述会信任 artifacts 真实性——**协议承诺与实现背离**。
- **修复方向**：要么在 `graph_update_execution_report` 内对 artifacts 逐个 `existsSync` 并把结果写进响应，要么改掉描述。

### S0-5 【网络暴露】Web 可视化服务默认绑定所有网卡
- **位置**：`src/web/server.ts:481` —— `server.listen(port)` 未指定 host，默认 `0.0.0.0`/`::`。
- **后果**：`graph serve` 启动后，同一 LAN 内任何设备可读取全部图数据（`/api/graph`）、节点内容、快照 diff（`:322-345` 还会把内部错误消息直接回显）。本地开发工具应绑 `127.0.0.1`。

### S0-6 【前端整页崩溃·补录】0.5.2 已发布包 `graph serve` 打开即黑屏（Svelte state_unsafe_mutation）
- **位置**：`web-ui/src/lib/store.svelte.ts:68-71`（`bucketOf` 桶未命中时 `_buckets[name]=newBucket()`）与 `:183-214`（全部 getter 经 `cur()` 走该路径；行号为修复前）。
- **现象**：浏览器控制台 `Uncaught Error: https://svelte.dev/e/state_unsafe_mutation`，栈含 `get graph`（bundle `index-tmljBUF5.js`），整页黑屏。
- **根因**：模板表达式（Svelte 5 编译为 derived）求值中读取 store getter → 桶未命中隐式建桶 = 变更 `$state` → Svelte 5 禁止 → 组件树崩溃。初始渲染时 WS 数据未到、`_buckets` 为空，首个被读的 getter 必崩。
- **漏测原因**：web-ui 测试在普通上下文调 getter（先 set 后 get），无 derived/真实渲染上下文覆盖；`tests/web` 只测纯函数与协议。**首审（本报告主体）亦未覆盖 web-ui 渲染路径**。
- **状态（2026-08-24 补录时）**：本地已修复——读/写路径分离（冻结空桶 `EMPTY_BUCKET` + `curReadonly()` 兜底，建桶只在事件/异步上下文），回归探针 `store-probe.svelte.ts` + `store-readonly.test.ts` 3 条，52/52 绿、svelte-check 0 错误。**npm 0.5.2 仍带病，需 0.5.3 补丁发布**；图 `fix-review-v052` 节点 f18 承接（验证收尾 + 渲染级冒烟回归 + 0.5.3 补丁包），随 P0 层汇聚 r0 交叉评审。

## S1 — 数据完整性与并发正确性

### S1-1 【毒化链】CLI 数值参数无 NaN/负数防护 → 写入非法 YAML → 全图读崩
- **链路**：
  1. `src/cli/create-node.ts:47`（`parseInt(options.level, 10)`）、`src/cli/update-node.ts:121,124`（`max_attempts`/`set_priority`）、`src/cli/next.ts:18`（`stale_ms`）——全部不查 `NaN`、不查负数；
  2. 写路径不校验：`src/core/parser.ts:78-83`（`writeNode` 直接 `yaml.dump` 落盘，**从不跑 schema 校验**）；
  3. 读路径才拒绝：`src/core/schema.ts:87-101`（`optNumber` 对 `NaN`/负数报 issue）→ `readNode` 抛 `SchemaValidationError`。
- **已验证**：`yaml.dump({level: NaN})` 输出 `level: .nan`，重新 load 得到 `NaN`。即一次 `graph create-node --level abc` 后，`status`/`next`/`get-node`/`snapshot`（凡走 `listNodes`，`src/core/node.ts:445-449`）**全部抛异常**，直到手工修文件。
- **架构根因**：校验只在读侧（"写脏、读炸"模式）。**写前校验缺失是系统性问题**，`writeNode`/`writeEdge` 落盘前应先跑 `validateNode`/`validateEdge`。

### S1-2 【校验双轨】CLI 接受负数 priority/max_attempts，MCP 拒绝——CLI 写入即自毒
- **位置**：`src/mcp/server.ts:864-865`（`z.number().int().min(0)`）vs `src/cli/update-node.ts:120-125`（无任何范围检查）。
- **后果**：`graph update-node --set-priority -5` 经 MCP 通道会被拒，经 CLI 通道成功落盘，之后该节点文件永久通不过自家 schema 校验（S1-1 的毒化实例）。

### S1-3 【并发覆盖】`createAdr` 的编号在锁外计算，锁内无重复检查 → 并发静默覆盖
- **位置**：`src/core/node.ts:481`（`nextAdrId` 在 `withLockSync` **之前**调用）、`:501-511`（锁内 `writeNode` 无 `existsSync` 检查）。
- **对比**：`createNode` 在锁内做了重复检查（`node.ts:46-49`），`createAdr` 没有。两个 MCP `graph_create_adr` 并发到达：双方都算出 `adr_0007`，后者**直接覆盖**前者的 ADR 内容，无任何报错与审计。

### S1-4 【丢更新】graph.yaml 引用列表的读-改-写完全无锁
- **位置**：`src/core/parser.ts:86-110`（`syncGraphRef`：readGraph → splice/push → writeGraph，无锁）；调用方 `src/core/node.ts:73`、`src/core/edge.ts:45` 只持有**各自节点/边 id** 的锁。
- **场景**：两个进程并发 `create-node`（不同 id，锁不互斥）→ 双方都基于旧 graph.yaml 读改写 → 一方的引用条目丢失。
- **缓释**：读路径全用 readdir，`graph rebuild`/`rebuildGraphRefs`（`parser.ts:125-136`）可重建。但 refs 是一份需要维护、会腐化、又是 validate 检查对象的"第二真相源"（架构问题 A1）。

### S1-5 【纪律后门】max_attempts 可经 `failed → cancelled → pending` 两跳归零绕过
- **位置**：`src/core/state-machine.ts:12`（`Failed → [Pending, Cancelled]`）、`:14`（`Cancelled → [Pending]`）、`:146-149`（cancelled→pending 时 `attempts: 0`）。
- **对比**：`failed → pending` 直接重试被 `:121-133` 的 max_attempts 硬拦截拦截。但两跳路径：第一跳无任何检查，第二跳**顺带把 attempts 归零**且不产生 `attempts_reset` 审计事件。MCP 通道无需 force 即可完成全部两跳。

### S1-6 【schema 与类型背离】必填字段校验缺失，`as T` 强转掩盖
- **位置**：`src/core/schema.ts:240-287` —— `validateNode` 仅强制 `id`/`label`；`type`（:248）、`status`（:257）、`attempts`/`max_attempts`/`level`/`created_at`/`updated_at` 全可选。而 `NodeSchema` 接口（`src/core/types.ts:121-153`）声明它们必填。`loadYamlFile` 末尾 `data as T`（`schema.ts:396`）把谎言编译掉。
- **可观察症状**：手写只有 id/label 的节点（`init.ts:90-92` 的 SCHEMA_DOC 明告用户"必填： id, label"——**文档鼓励写出会让下游崩的文件**）：
  - `src/core/index-service.ts:295-297`：`summary[n.status]` 以 `undefined` 为键，产出 `"undefined": N` 的垃圾分布；
  - `src/cli/status.ts:31-34`：同样打印 `undefined: 1`；
  - `allowedTransitionsFor`（`state-machine.ts:34-42`）对 `undefined` 状态静默返回空数组。

### S1-7 【缓存失效失准】`invalidateIndex` 与 `buildGraphIndex` 的缓存键不一致
- **位置**：`src/core/index-service.ts:208`（键 = `path.resolve(toGraphDir(rootDir))`）vs `:232`（删除 `path.resolve(rootDir)`）。
- **问题**：当调用方传入工作区根时，`toGraphDir(rootDir)` ≠ `rootDir`，内存缓存条目**删不到**。当前 MCP 全程传图目录未爆发，Web/测试/第三方若混用两种传法，"写后读不一致"就会复发。

### S1-8 【校验错位】edge 的 contract 校验查了不存在的字段，真正的字段从未校验
- **位置**：`src/core/schema.ts:307` —— `optEnum(data.contract, "method", [...])` 校验的是 `contract.method`；但 `Contract` 类型（`src/core/types.ts:156-160`）没有顶层 `method`，方法在 `contract.validation.method`。`contract.consumed_by` 的元素结构（:308-310）也只查"是数组"不查元素。MCP 的 `graph_add_edge` 把 contract 作为自由 `z.record` 透传（`server.ts:824-827`）。

### S1-9 【语义漂移】`--reset-attempts` 单独使用时 CLI 静默无效，MCP 正常
- **位置**：`src/cli/update-node.ts:131-134` —— `if (Object.keys(updates).length === 0) { 提示; return; }` 早于 resetAttempts 处理。MCP 对应检查是 `length === 0 && !reset_attempts`（`src/mcp/server.ts:901`）。
- **后果**：`graph update-node -i x --reset-attempts` 什么都不做且**退出码 0**。

### S1-10 【半重置】旧式单图 `init --force` 只清 graph.yaml 不清节点文件
- **位置**：`src/cli/init.ts:57-83` —— `--force` 重置路径将 graph.yaml 写为 `nodes: [], edges: []`（:69-78），但不删除既有 `nodes/*.yaml`（仅 mkdir，:79-81）。
- **后果**：重置后 readdir 仍列出全部旧节点，graph.yaml 却声称 0 引用——永久性自相矛盾状态。对比带名 init 的 `--force` 走 `trashGraph` 整目录回收（:29-32），语义正确。
- **附带**：该路径创建目录清单（:79）含 `index` 但缺 `.locks`，与 `createGraph`（`graph-dir.ts:282`）不一致。

### S1-11 【快照撕裂】snapshot/rollback 与节点写入之间无互斥
- **位置**：`src/core/snapshot.ts:89-93` 注释自认只对同类操作加了 `__snapshot__` 锁；但 `createSnapshotUnlocked`（:105-151）逐文件 `copyFileSync` 期间，`writeNode`（只持节点级锁）可自由穿插 → 快照可能混装"新节点文件 + 旧 graph.yaml"。全量回滚（:303-322）同理。

## S2 — CLI 与 MCP 功能完整性 / 语义漂移

### S2-1 MCP 工具面缺 `validate`、`events`、`export`、建图四类能力
- **位置**：`src/mcp/server.ts` 全文 22 个注册工具 vs CLI 27 个命令。
- **具体缺口**：
  - **无 `graph_validate`**：批量创建官方指引"崩溃后重跑"（`server.ts:726-727`），但 agent 创建完环/幽灵边后**没有任何 MCP 手段自检**——环检测、schema 汇总、六条领域规则全部只在 CLI（`src/cli/validate.ts`）；
  - **无 events 读取**：审计日志（`eventlog.ts`）只能 CLI 看，裁决 agent 无法回溯 force_override/attempts_reset 历史；
  - **无 export**（mermaid/docs）；
  - **无建图/删图**（若刻意为之应在工具描述中说明）。
- **工具计数腐烂**：`src/mcp/server.ts:3` 注释"18 个 graph_* 工具"，实际注册 22 个。

### S2-2 `graph_switch` 在 `SUPER_PLUMBER_GRAPH` 环境变量存在时静默失效
- **位置**：`src/mcp/server.ts:302`（无条件 `setProcessActiveGraph` 后返回成功摘要）+ `src/core/graph-dir.ts:173-178`（优先级链 env > process）。
- **后果**：设置了该环境变量的用户调用 `graph_switch`，工具返回 "✅ switched" 的完整成功响应，但下一次任何工具调用仍解析到 env 指定的图。**返回值撒谎**。

### S2-3 `graph diff --from` 的默认值与两处文档描述不符
- **位置**：`src/mcp/server.ts:1138`（描述："from: 默认最新快照"）vs `:1145-1149`（仅当 `to === undefined` 才回填最新快照）；CLI 同构 `src/cli/diff.ts:7,13-18`。
- **后果**：`graph diff --to snapX` 实际语义是 "working → snapX"，而非文档暗示的 "最新快照 → snapX"。

### S2-4 checkpoint 聚合函数与 passed 硬门禁对 "passed+skipped" 判定矛盾
- **位置**：`src/core/state-machine.ts:154-162` —— `[passed, skipped]` 混合时落进兜底返回 `"pending"`；而 `assertPassedEligible`（:69-85）明确允许 passed/skipped 全完成。
- **后果**：`get-node`/`graph_get_node` 对已满足完成条件的节点显示 `checkpoint_aggregate: pending`，误导裁决 agent。

### S2-5 `validate` 对 max_attempts=0（不限重试）的节点误报超限
- **位置**：`src/cli/validate.ts:106` —— `node.attempts > node.max_attempts`。`max_attempts: 0` 语义是"不限"，但 attempts=2 > 0 即触发误报。判定应为 `node.max_attempts > 0 && attempts > max_attempts`。

### S2-6 `validate` 引用完整性只校验单方向
- **位置**：`src/cli/validate.ts:210-223` —— 只查 "graph.yaml refs → 文件存在"，不查 "文件存在 → 有 refs"。S1-4 的丢引用竞态与 S1-10 的半重置产生的正是后者方向的漂移，validate 一律沉默。

### S2-7 公开 API barrel 不导出 v0.5.2 多图 API
- **位置**：`src/core/index.ts:3-12` 只导出 10 个模块；`graph-dir.ts`、`domain.ts`、`eventlog.ts`、`docs-export.ts`、`index-service.ts` 均未导出。而注释（:2）明令第三方"**禁止深挖 dist 内部路径**"。头号特性对库用户不可用。根入口 `src/index.ts` 更是只转口 types 一行。

### S2-8 `graph_search` 绕过索引缓存，与 `graph_get_graph` 的 I/O 模型不一致
- **位置**：`src/mcp/server.ts:589`（`listNodes(rootDir)` 全量读盘）vs `:424`（`buildGraphIndex(useCache: true)`）。search 是 agent 高频工具，却是唯一不走红路径缓存的读取工具。

### S2-9 Web `/api/graph` 与 WS 初始推送不做缓存全量扫盘
- **位置**：`src/web/server.ts:303`、`:389` —— `buildGraphIndex(target.apiRoot)` / `buildGraphIndex(dir)` 均未传 `{useCache: true}`。对照 watcher 推送路径 `:414` 明确用了缓存。

### S2-10 fallback / iterates 边类型是"装饰性"的——MCP 描述仍在推销
- **位置**：`src/cli/validate.ts:152-159` 警告"工具未实现其运行时语义"；但 MCP `graph_add_edge` 描述（`server.ts:814`）仍把 fallback/iterates 列为可用的控制流表达。

### S2-11 MCP 全部审计事件的 actor 恒为 `"mcp"`，agent 身份丢失
- **位置**：`src/mcp/server.ts` 各工具统一 `{ actor: "mcp" }`（如 :658, :692, :947）；`claim_by` 只落进事件 `detail`（`src/core/node.ts:281-283`）。多 agent 并发时审计日志无法按执行者追责。

### S2-12 MCP 幂等 re-claim 短路返回，不留任何审计痕迹
- **位置**：`src/core/node.ts:218-223` —— 同一 claimBy 重复认领直接 `return node`，不经过 `appendEvent`。

## S3 — 代码质量、健壮性与性能

### S3-1 `as never` 类型逃逸滥用（MCP 参数层类型安全形同虚设）
- **位置**：`src/mcp/server.ts:655`（`checkpoints as never`）、`:784`、`:800`、`:840`、**:841（整个参数对象 `} as never`）**、`:256-257,296` 的 `("running" as never)`。

## 架构级系统性问题（跨切面）

**A1. 双真相源：graph.yaml refs vs 目录 readdir。**
refs（`types.ts:192-193`）由 `syncGraphRef`/`rebuildGraphRefs`（`parser.ts:86-136`）维护，但所有读路径一律 readdir，refs 没有任何读消费者，只有 validate 读它。它因此成为：并发丢更新点（S1-4）、半重置矛盾点（S1-10）、单向校验盲区（S2-6）的共同根源。要么让 refs 成为唯一 listing 来源（写时加锁），要么删掉 refs 让 graph.yaml 只存 entry/exit。

**A2. 校验架构："读时校验、写时放行"。**
`writeNode`/`writeEdge`/`writeGraph`（`parser.ts:55-60,78-83,235-240`）落盘前一律不跑 schema 校验。任何上游校验缺口（CLI NaN、负数、MCP `as never`、手编文件、第三方库调用）都会变成**落盘成功 + 后续全图读取失败**的延时炸弹。S1-1/S1-2/S1-8/S3-12 四个独立 bug 都是这一架构的同型症状。在写路径加校验是消灭整类问题的单点修复。

**A3. 锁体系只覆盖"单节点写"，不覆盖任何多文件操作。**
节点级锁护住了 claim 原子性，但 graph.yaml（S1-4）、快照/回滚（S1-11）、`rebuildGraphRefs`、工作区事件（S3-6）、ADR 编号（S1-3）全部在锁体系之外。

**A4. CLI 与 MCP 双通道双轨校验，且强弱方向不一致。**
MCP 有 zod（数值范围严），CLI 靠手写 if（漏 NaN/负数）；checkpoint id CLI 严、MCP 松；`reset-attempts` MCP 对、CLI 错（S1-9）；contract 结构两边都不真正校验（S1-8）。没有一个共享的参数校验层。core 层本应是唯一执法点（写前校验，A2），补上后双轨问题自然消解。

**A5. 文档/描述与实现的历史漂移无机制约束。**
"18 个工具"（S2-1）、artifacts 校验承诺（S0-4）、diff 默认值（S2-3）、fallback/iterates 语义（S2-10）——四处"承诺-实现"背离全部靠人肉同步。工具描述是 agent 的 API 文档，可断言的描述应纳入测试。
