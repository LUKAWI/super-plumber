## A. 工具层缺陷（0.7.0 已发布代码）

### A1. ADR 编号按图独立 × 共享知识视图目录 = 跨图视图冲突【已实证；隔离绕过中；根治待版本】
- **现象**：① 0.8.0 设计文档预期五张新 ADR"接续账本编号 0004-0008"，实际在 v080 图内创建
  编号为 adr_0001~0005——**ADR 编号是按图独立的**（实证：default 图另有 adr_0001-0003，
  multitool-refactor 图自有 adr_0001/0002，各图编号互不相干）；② v080 打快照时自动导出把
  default 图的 `docs/adr/0001-0003` 三视图挤进 `.retired/`、并用 v080 的五张覆写同号文件名，
  同时把 `CONTEXT-MAP.md` 从其他图的 5 个 context 覆写为 v080 的 3 个（现场已用
  `git checkout -- docs/adr` + `git clean -f docs/adr` 复原，终态 git status 已核对）。
- **根因**：① `graph_create_adr` 自动编号按当前图内已有 ADR 数起算，无工作区全局账本概念；
  ② `graph export --docs` 与 `graph snapshot` 的自动导出都落**工作区共享目录**
  （`docs/adr/`、`CONTEXT-MAP.md`、`docs/contexts/`），`retireStaleSlugFiles` 对"同号异名"
  旧文件做 `.retired/` 归档——多图工作区下任何一张图导出都会挤掉其他图的视图；③ snapshot
  的自动导出**没有** `--adr-dir`/`--ctx-dir` 透传（CLI export 有，snapshot 没有），无法在
  快照路径上隔离。
- **证据**：`src/core/docs-export.ts`（retireStaleSlugFiles 归档逻辑 + runDocsExport 写
  `workspaceOf(rootDir)` 共享目录）；`src/core/snapshot.ts` 快照自动导出注释（"随快照点落盘"）；
  `src/cli/export-mermaid.ts` 的 `--adr-dir`/`--ctx-dir` option（仅 export 侧）；多图 ADR 并存
  实证见 `.graph/default/nodes/adr_000*.yaml` 与 `.graph/multitool-refactor/nodes/adr_000*.yaml`。
- **现行缓解**（已固化进 v080 节点 g080-adr-promote 的 plan/DoD）：ADR 视图导出改走
  `graph export --docs --adr-dir docs/adr/v080` 隔离目录（DoD 断言"默认 docs/adr 零触碰、
  无新增 .retired/"）；CONTEXT-MAP/docs/contexts 按当前开发图口径接受覆写（图是真相源，
  视图可再生，git 可复原）。
- **修复方向**（互斥方案需过 ADR 三判据）：工作区全局 ADR 编号（账本图/注册表）／图名前缀
  编号（`v080-0001`）／snapshot 增加目录透传。Q9（自举图 ≥6）放大此问题的暴露面。
- **残留**：根治未做；0.8.0 靠隔离目录绕过。

## B. 提示词/文档资产缺陷（0.6.1 重构残留）

### B1. SKILL.md 双副本脱离同步门禁【实证存在差异；防漂移目前只靠人肉】
- **现象**：`.pi/skills/*/SKILL.md`（正本）与 `integrations/plugin/skills/*/SKILL.md`（插件
  包拷贝）是手工维护的双副本，而 `scripts/sync-integrations.mjs` 的 SOURCES 只含
  manual/commands/sp-scripts（源码注释明言"对提示词类文件不做任何处理"）——**skills 完全
  不在 sha256 同步门禁内**，`prepublishOnly` 也不覆盖。
- **证据**：`scripts/sync-integrations.mjs` 头部 SOURCES 定义；实测两渠道四份 SKILL.md 现存
  3+1 处差异（均为 ADR-0001 寻址行的本地化注记——设计上允许，但也意味着字节级断言天然
  不可用，同步检查必须做语义级或生成式）。
- **影响**：改 `.pi` 漏改 `integrations/plugin` 时，Claude/ZCode 渠道静默发布漂移话术，
  无任何门禁报警。0.8.0 的四个 skill 改动项（WF01-04）全部踩此面——v080 对应节点的
  文件边界已显式列双路径、DoD 加"两副本 diff 仅寻址行差异"核对来规避。
- **修复方向**：短期 = PR 模板加"skill 改动必须双路径 diff"检查项（0.9.4 S06 顺带）；
  根治 = 0.9.4 S01 单真相源重组（正本收拢 `integrations/src/`，`.pi/` 与 plugin 变构建
  产物，寻址行差异做模板变量注入）。
- **残留**：根治归 0.9.4（主线 B，已排期）；短期检查项未落地。

## C. 工作流/skills 层缺口（第一轮设计暴露）

### C1. 多关注点图的领域建模可被整体略过，当前版本无任何机器信号【事件复盘；修复方向已列】
- **事件**：v080 第一轮设计产出 11 个工作流节点、**0 context、0 ADR**，设计报告亦缺
  sp-designer 输出规范强制要求的领域段（"知识顶点: context {C} 个 / ADR: {K} 篇"）；
  `graph validate` 0 error 0 warning、doctor 仅命名类 warning——**没有任何机制拦住
  "只写工作流拓扑、略过 CONTEXT/ADR"的设计**，直到用户人工审出。
- **根因链**：① 直接原因是编排方（主控）派单违反 plumber-design Step 2 铁律——"需求跨多个
  关注点 → **领域建模与 ADR 甄别是 designer 必做项，点名不可裁剪**"——漏了派单模板第 1/3/4
  条（含领域结构的任务目标、首行 `Read integrations/shared/manual.md §2、§6`、信息优先级
  声明），且主动把 context 降为"可选"、把 ADR 推迟到执行节点；designer 依"派单＞角色提示词"
  的优先级规则照办——**规则被正确执行，错在上位派单**。② 防御纵深缺失才是版本缺陷：派单
  合规全靠人自觉，designer 报告无机器校验，validate/doctor 的 E/W 项完全不覆盖
  "多节点图零知识顶点"。
- **修复方向**（分层，均为轻量改动）：skills 层 = plumber-design 派单模板尾加三条合规
  自查清单（缺一不派发）；体检层 = doctor 加 W 级提示（工作流节点 ≥N 且 context=0 →
  建议评估 bounded context 划分；ADR=0 不提示——单关注点小任务合法）；报告层 =
  designer 输出自检"报告缺领域段 = 未完成"。
- **残留**：未修；是否挤进 0.8.0 由用户定（倾向 0.8.x 补丁，不阻塞 P0）。

### C2. super-mario agent 类型在 ZCode 会话 spawn 缺工具【平台侧；代行绕过中】
- **现象**：2026-08-30 同一会话连续两次 spawn `super-plumber:super-mario`，可用工具均仅
  `RespondToCoordinator` 一个函数（无 Read/Bash/Grep/任何文件工具），裁决任务两次如实
  挂起、零伪造结论。
- **排除项**：agent 定义本身正确——插件缓存（0.6.1 包）与 `.pi` 正本的 frontmatter 均为
  `tools: read, bash, grep, find, ls` 且内容一致；同会话 `sp-designer` spawn 工具齐全，
  说明是**类型相关的供给问题**（harness 侧插件 agent 工具解析），非 SP 资产错误。
- **影响**：ZCode 下裁决/审核角色不可用。绕过已验证可靠：general-purpose 全工具 subagent
  按同纪律代行（提示词写死只读红线 + "缺工具即如实挂起"），本次三轮审核均由其完成
  （validate/doctor/diff/next 全部亲自复跑取证）。
- **修复方向**：平台侧排查插件 agent 的 tools 供给链（SP 代码不可修）；SP 侧可选加固——
  super-mario 定义"首步指令"加一句自检（无文件工具即挂起上报，本次行为证明有效），
  或 manual 已知问题注明。
- **残留**：未修（平台问题）；代行模式作为既有事实记入工作流经验。
