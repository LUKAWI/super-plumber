# 0001 — 三工具集成采用分别手写维护，否决单源生成器

pi 集成维持 .pi/ 直写现状；claude code 以 .claude-plugin 插件文件夹独立成型；zcode 以 .zcode-plugin 插件文件夹独立成型。三者的 agent 提示词与 skill 正文分别手写维护，否决「单一真相源模板 + graph integrate 生成器」路线。配套补偿：Operations 手册、斜杠命令文案、sp-*.mjs 等机械共享件采用「一份正本 + 构建期同步脚本」保持一致。

**Status：** superseded（由 ADR adr_0002 接替）

**Context：** 重构对齐时曾推荐「integrations/src 单一真相源模板 + graph integrate 生成器」路线（决策树问题4）；实际发现 pi/zcode/claude 三家的 frontmatter 字段（injectAgentsMd、model 绑定、commands 组织）互不通用，同一角色的最佳表达在三工具中天然不同；同时官方 example-plugin 展示了双 manifest 同目录的插件形态可作为独立成包的样板。

**Considered Options：** A. 单源模板+生成器：一致性最强，但模板工程量大、三边措辞被压平趋同、调试绕一层；C. 单文件内嵌多工具变体块：省文件数但可读性与维护性差；B（选中）：分别手写三套——各格式获得完全的措辞自由度与就地可读性，代价是文本改动需人工同步三处，由归属清单与契约边（cross_review）约束。机械共享件（手册/命令文案/sp 脚本）则反向收敛：一份正本+构建期同步脚本保证三拷贝零 diff，作为该决策的一致性底线。

**Why：** 用户明确裁断：不做生成器，分别写。理由是三个目标格式的提示词在不同模型/工具下的最佳表达本就不同，手工分别润色的质量优先于模板化的机械一致；而真正的漂移风险集中在机械共享件上，这部分已用同步脚本闭环。

**Consequences：** 角色提示词或 skill 语义变更需人工同步三处，漏改风险靠段落归属清单、e09/e10/e13 契约边的 cross_review 核查以及发布前冒烟兜底；新增第四个目标工具的成本是整包新增而非配置项；graph integrate 类命令不再规划于本版本。
