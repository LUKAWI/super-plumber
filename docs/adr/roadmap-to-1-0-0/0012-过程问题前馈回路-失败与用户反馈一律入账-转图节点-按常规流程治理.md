# 0012 — 过程问题前馈回路：失败与用户反馈一律入账、转图节点、按常规流程治理

设计/开发/验证/测试全过程中每一次失败遇到的问题，以及用户提出的修改要求，一律三步走：（1）记入统一问题账本 docs/issue-log.md（现象、根因、证据、修复方向、紧急度、状态）；（2）可行动项转化为 ctx-issue-log（问题修复域）的任务节点，按一般节点方法处理（claim→checkpoint→report→verdict→passed），priority 按"越紧急越优先"排定；（3）解决后节点标 passed 并在账本销账。不可行动项（纯操作坑、已由其他节点覆盖的问题）在账本记录处置理由即可，不建节点。与既有 L1 修复层（fix-v080-*，源自 v0.8.0-issue-log.md 的产品缺陷）的关系：产品缺陷走修复层，过程性问题走本域，两边账本互相 cross-reference、不重复建节点。

**Status：** accepted

**Context：** 2026-08-30 v080 全版本扩展设计与调试过程：批量脚本 glob 污染节点标签、graph_traverse 深度截断静默丢节点（truncated:false 虚报）、level 编码过度（33 层）被用户审出——这些"过程发现"散落在会话与记忆里，没有进入图的治理闭环。用户 2026-08-30 拍板：把此类问题的处理制度化。

**Considered Options：** ① 只写 issue log 不入图——无调度无状态无 priority，问题会烂尾在文档里；② 每次失败直接热修不留痕——无凭据、同一坑反复踩；③ 本方案：账本 + 专门域 + 常规节点流转（采纳）。

**Why：** 图是唯一真相源与调度器——问题只有变成节点才有 priority、状态机与验收凭据；专门领域避免过程性问题与 roadmap 功能条目混编；passed 语义给"修没修"以可查凭据；用户反馈本身就是最高优先级的需求来源，入图才不会被会话遗忘。

**Consequences：** ctx-issue-log 域成为常驻治理面：节点随开随销，priority 反映紧急度；设计期即时修复（如本次 level 重编）同样入账并当场走完 passed 流程留凭据；账本文件入库（git tracked）随仓库演进；与 L1 修复层（fix-v080-*）并存互补，账本互相 cross-reference。
