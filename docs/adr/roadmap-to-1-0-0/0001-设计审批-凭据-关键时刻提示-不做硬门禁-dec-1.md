# 0001 — 设计审批：凭据 + 关键时刻提示，不做硬门禁（DEC-1）

新增 graph approve（CLI 命令 + MCP graph_approve），向 graph.yaml 写可选 review: {status, by, at} 字段 + design_approved 审计事件；graph_get_next_actions 的 ready_eligible（冷启动）条目与 claim 响应附一行 review_flag（如 unreviewed）提示。核心状态机不新增任何拒绝规则——未审核的图行为与 0.7.0 完全一致（零迁移、零默认拒绝）。plumber-design / plumber-execute 现有“未批准绝不执行”话术保留，designer 在 serve 人审通过后调一次 approve 落凭据。

**Status：** accepted

**Context：** 反向审查发现：SP 的 17 种审计事件中没有任何“设计审核通过”类凭据，graph.yaml 无审批字段——“人审硬门禁”实际只存在于 skill 文本，审过的图与没审过的图在工具层不可区分，与“agent 想糊弄？状态机先不答应”的产品宣言自相矛盾。第一轮讨论曾提议升级为状态机硬拒绝（unreviewed 禁 claim），用户否决。

**Considered Options：** ① 状态机硬拒绝（unreviewed 禁 claim）——被用户明确否决：拒绝点远离被管动作（跳过审核的 agent 在 claim 时才被拦）、爆炸半径是整图、每个认领 agent 新增一条失败面；② 快照当凭据（审核通过时打快照）——零 schema 改动但语义藏在惯例里，且弄脏 diff/rollback 语义；③ 只发事件不写字段——读取退化为 O(events) 扫描，查询态更差；④ 本方案：凭据字段 + 两处 nudge（采纳）。

**Why：** 硬门禁的适用判据（见 DEC-3）三条全不满足：跳过设计审核的代价是浪费功夫（执行得差、三层验收打回），不是污染共享状态（claim/report/passed 语义依然正确）——前者归 skills 纪律管，后者才归状态机管。而“审没审过”的可区分性（凭据）几乎免费：字段写入一次、事件 append-only 运行时不读、提示只在决定时刻出现（ready_eligible / claim 响应各 ~10 token）。提示放在决定的那一刻比写在 skill 正文更可靠——模型读过长上下文后最容易丢的是文档开头的流程约束（lost-in-the-middle），nudge 是把纪律提醒从文本搬到时序上。该机制是 SP 已有 adr_flags 模式（“⚠️ 决策依据已过时”）的平移，非新发明。

**Consequences：** ① 向后完全兼容；② skill 正文零增长（工具会提示的事不在正文复述——no-op 原则）；③ 升级通道保留：将来出现多人共享 .graph、陌生 agent 自动认领的场景时，“未审核被执行”从浪费自己变成污染共享状态，届时把 flag 升级为硬门禁是一行代码（先留凭据、后升强制，与 fallback/iterates 的文档性标注哲学同构）；④ 红线：响应里只回枚举/一行短语，不回审批对象全文、不把审批理由注入每次响应（“只注入指针永不全文推送”的上下文经济红线同样适用）。
