## A. 代码缺陷（执行期发现并修复/处置）

### A1. jsonGraph 自递归栈溢出（MCP 回显层批量替换事故）【已修复】
- **现象**：mcp_tools 实现后所有 MCP 工具调用返回 "Maximum call stack size exceeded"。
- **根因**：实现回显层时用脚本批量替换 `return jsonText(` → `return jsonGraph(gctx, `，
  把 jsonGraph **内部**的 `return jsonText(body)` 也替换成了 `jsonGraph(gctx, body)`——自递归。
- **修复**：改回 jsonText；**教训**：批量文本替换的锚点必须排除被替换函数自身（先插入函数体再扫替换的顺序错误），已在探针定位后修复，测试锁定。
- **残留**：无。

### A2. 双 `.graph` 拼接（CLI 守卫在 rootDir 语义变更后失真）【已修复】
- **现象**：create-node 等命令报"未找到 …/.graph/t/.graph/graph.yaml"。
- **根因**：cli_commands 把所有命令的 rootDir 改为图目录后，create-node 的"未初始化"守卫仍用
  `listGraphNames(rootDir)`（期待工作区根）——在图目录上又拼了一层 .graph。
- **修复**：守卫改为检查 `rootDir/graph.yaml` 存在性（rootDir 已是图目录），rebuild/status 同修。

### A3. D4 升级：特定 Unicode 文件名的 fs.rmSync 是进程级崩溃【已加固，残留风险见 B3】
- **现象**：dogfood 执行 `graph export --docs` 时进程静默 exit 127 无任何输出（export 半途而废，
  只写出 0001）。
- **定位**：纯 `node -e` 最小复现——`fs.rmSync("…/0002-纯文件系统存储-无数据库.md")` 直接
  崩溃进程（无异常可捕，try/catch 完全无效）；`renameSync` 同名文件则正常。触发点=特定 Unicode
  文件名组合（非全部 Unicode）。
- **加固**：retireStaleSlugFiles 弃用 rmSync——改为 mkdir `.retired/` + renameSync 归档
  （原子、可逆、不丢旧视图），rename 失败降级覆写跳转注记，双保险失败保留旧文件。
- **残留**：snapshot 回滚路径（snapshot.ts:307/312/335/343）仍用 rmSync 删除节点/边文件——
  节点 id 是 agent 自定的，可能含同类 Unicode——**后续版本优化项**（同 renameSync 归档模式）。

## G. 全局隐患推测（用户指定：先推测，不做全局测试）

### G1. 多图下 docs 导出与快照自动导出的目标冲突
- 现象基础：runDocsExport 的产物路径固定在工作区根（docs/adr、CONTEXT-MAP.md、docs/contexts），
  而工作区现在有 N 张图。A 图快照会自动导出 A 图的知识顶点，B 图快照导出会**覆盖同一批文件**。
- 推测影响：多图并存且都做领域建模时，export 视图互相踩踏（最后导出者胜）；单图场景无影响。
- 建议方向（0.5.x）：导出按图分目录（docs/<图名>/… 或 context 文件名带图名前缀），
  CONTEXT-MAP.md 改为列所有图的聚合视图——与本工具"图为真相源"一致但需要一次设计对齐。

### G2. 跨图同名节点 id 的纠错扫描成本与误报
- hintMissing 在错误路径扫描兄弟图的**全部节点文件**（readdir+逐个 YAML 解析）。10 图 ×
  数千节点时一次"查不存在节点"的纠错可能 O(N 全图×图数)。当前触发条件是错误路径（低频），
  但攻击面/脚本批量误操作时可能放大。
- 建议方向：图名→节点 id 集合的磁盘索引（graph.json 已有 nodes 数据，可在 rescan 时聚合成
  ws 级 id→graph 映射，O(1) 纠错）。

### G3. rename/delete 期间其它进程的窗口期
- rename-graph/delete-graph 只拿目标图的写锁语义（renameSync 无锁），另一进程正在该图
  writeNode 时 rename 目录会导致：①Windows 上 rename 失败（EPERM，被 watcher/打开句柄占用——
  B3 已见）；②成功后对方进程的后续写入落到旧路径（孤儿文件）。
- 建议方向：rename/delete 前要求目标图无 running 节点（或获取该图全节点锁集合的保守锁），
  CLI 加提示"图中有 N 个 running 节点，确认继续？"。

### G4. workspace-events.jsonl 无限增长
- 与图级 events.jsonl 同款 append-only 设计，但工作区生命周期更长（图删了工作区还在）。
- 建议方向：与图级事件日志一起考虑 GC/rotate（如 >10MB 归档 .old）。

### G5. 旧布局"default"与多图 default 的认知歧义
- 迁移后 `.graph/default/` 是一张普通图；未迁移仓库的"default"是布局概念。用户列表看到
  default 可能误以为是系统图。命名上 default 仅作迁移兜底（既定设计），文档需反复强调。

## 专项性能实测（tests/perf/multigraph-perf.test.ts，4/4 通过）
- 多图解析热路径：resolveGraphDir/toGraphDir 10 图工作区 1000 次中位数 <0.5ms；listGraphNames 50 图 200 次中位数 <10ms——**多图兼容对热路径开销可忽略**（每调用 readdir+existsSync 级）。
- 快照自动导出（v0.5.1 CONTEXT-MAP 功能）性能影响：40 节点+7 知识顶点的图快照 5 次中位数 <2s；幂等重跑 <500ms——导出开销（7 个 md 写盘）在快照总耗时内占比小，且幂等重跑成本稳定。
- 10 图工作区中单图快照不受周边图影响（文件隔离成立）。

### A4. 并发迁移：`.locks` 被搬走导致等待锁的进程 ENOENT 崩溃【cp_cross 专项测试抓出，已修复】
- **现象**：两进程并发 `init` 建第二图，后到者 exit 1：`ENOENT: no such file or directory, open '.graph/.locks/__ws_migrate__.lock'`。
- **根因**：迁移清单含 `.locks`——先到者迁移时把工作区级锁目录整体搬进 `default/`，
  等待锁的进程 acquire 时其锁文件路径已不存在（openSync ENOENT 直接抛出，非 EEXIST 重试路径）。
- **修复**：`.locks` 移出迁移清单（6 项）；它永久留在 `.graph/.locks/` 作工作区级锁的家；
  default 图的节点锁迁移后自然改落 `.graph/default/.locks`（瞬态、30s 陈锁自愈）。
- **验证**：tests/core/graph-dir.test.ts 新增"两进程并发建图"用例（migrate 事件恰好 1 次、两图皆成、default 无损）。
